# Codex Coding Standards

Failure-mode rules for code generated by OpenAI Codex. Rules were developed empirically from Phase 10 of the MySitter project (2026-04-18), where Codex was used in place of Gemini as a deliberate comparison experiment.

Rules are ordered by category; numbers are stable references — do not renumber when adding.

---

## Sandbox Artifacts

**C1. Verify text file encoding after generation**
After any file is generated by Codex, check its encoding with the `file` command. If it reports UTF-16, re-encode to UTF-8 before using it.

```bash
file apps/api/requirements.txt
# "Unicode text, UTF-16, little-endian text" → re-encode:
python3 -c "
with open('requirements.txt', 'r', encoding='utf-16') as f:
    content = f.read()
with open('requirements.txt', 'w', encoding='utf-8', newline='\n') as f:
    f.write(content)
"
```

This is most dangerous for `requirements.txt`, `.env*`, and any config file that pip or a build tool parses as plain text. Codex's sandbox environment may tolerate the encoding; a real pip install will not.

**Why this happens:** Codex runs pip install in its sandbox and reports success, but the file was written with UTF-16 encoding. The sandbox doesn't surface the encoding mismatch because some environments handle it; a standard Linux pip install fails silently or crashes.

## Plan vs. Codebase Disagreements

**C2. Codex may use the actual codebase as ground truth when it disagrees with the plan**
When the plan spec and the actual implementation disagree (e.g. plan says `PATCH /bookings/{id}/confirm`, actual endpoint is `@router.post(...)`), Codex tends to use what the code says rather than what the plan says. This is generally correct behavior — the code is authoritative.

However, always verify this by reading the actual endpoint/method definition. Do not assume Codex matched the plan unless you check.

## Comparison vs. Gemini

| Dimension | Codex | Gemini |
|---|---|---|
| Missing files | Rare — follows file lists in plans closely | Common — skips infrastructure/CI steps |
| Logic bugs | Low | High (3–9 per phase) |
| Over-engineering | Low — stays close to spec | High — adds parallel implementations, unsolicited abstractions |
| Encoding/artifact issues | UTF-16 file encoding | None observed |
| HTTP method accuracy | Reads actual code (good) | Follows plan spec (may be wrong if plan is stale) |
| Test structure | Well-structured fixtures | Tends to use hardcoded IDs / improper mocking |

**General guidance:** Codex output requires fewer logic-level fixes but benefits from a mechanical file encoding check. Gemini output requires deeper architectural review.
