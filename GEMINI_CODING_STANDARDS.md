# Gemini Coding Standards

Global coding standards and failure-mode rules for all projects. All code generated by Gemini must adhere to these rules. Rules are ordered by category; numbers are stable references — do not renumber when adding.

---

## Frontend — React / React Native

**F1. `enabled` guard on every conditional query**
Any `useQuery` that should only fire for certain roles, states, or conditions MUST pass an explicit `enabled: <boolean expression>` parameter. Never rely on error-handling (`onError`, status checks) to suppress requests that should not be made. The API returns hard errors (402, 403) for unauthorized callers — these errors must never fire in the first place.

**F2. QueryClientProvider placement**
Never call `useQuery`-based hooks in the same component that provides `QueryClientProvider`. Hooks run before `return`, so the context doesn't exist yet. Split into an outer provider component and an inner consumer component.

**F3. StrictMode double-invoke guard**
Any `useEffect` that calls a mutating API (POST/PATCH/DELETE) must be guarded with a `useRef(false)` flag set before the call. React 18 StrictMode double-invokes effects in development.

**F4. Use shared types — never redeclare locally**
API response types come from the shared types package. Never redeclare inline object types for API payloads or responses.

**F5. Verify field existence before use**
Before referencing any field on a typed object, confirm the field exists in the canonical type definition. Do not assume a convenience field exists because it would be useful.

**F6. No stub `onClick`/`onPress` handlers**
Every `onClick`/`onPress` must be fully implemented. If a feature is not ready, disable the button (`disabled={true}`) or remove it from the JSX. Never ship a dead interactive element.

**F7. All imports must be used**
Every imported hook, component, or value must appear in the component body or return block. An import that is never referenced must not exist.

**F8. Match all JSX opening/closing tags**
Triple-check every closing tag matches its opening tag exactly, including casing. Typos in closing tag names crash the renderer and produce misleading error messages.

**F9. `ApiClient` namespaces are class properties, not methods**
When adding a namespace to `ApiClient`, declare it as a class property with an object literal, not as a method returning an object. Methods break `this` binding.

**F10. Object params, not positional**
Always match the TypeScript signature of API client methods. Pass named parameter objects — never positional arguments that happen to fit by accident.

**F11. Mobile uses relative imports only**
`apps/mobile` has no `@/` path alias configured. Every import in a mobile file must use a relative path. Do not copy import paths from the web app — they often differ.

**F12. Verify mobile export names against source**
Mobile imports must be checked against the actual source file. Do not copy export names from memory or from the web app — named exports often differ between packages.

**F13. Import hygiene after deletions**
When a method is removed from a service, simultaneously remove every import of that method in every file that referenced it. Never leave stale imports — they cause TypeScript errors and, in Python, `ImportError` at startup.

**F14. Presigned URL content-type must match actual file**
When calling an upload presign endpoint, pass the actual file's content type from `file.type`. Never hardcode `"image/jpeg"` for a file input that accepts `image/*`.

## Backend — Python / FastAPI / SQLAlchemy

**B1. SQLAlchemy 2.x count pattern**
Always use `select(func.count()).select_from(q.subquery())`. Never use `.with_only_columns(func.count())` on a filtered query — that is a 1.x pattern that silently drops WHERE clauses in 2.x.

**B2. Never import from the app entry point in routers**
The app entry point (e.g. `main.py`) imports all routers, so any router that imports back from it creates a circular import that crashes startup. Shared infrastructure (rate limiters, app state, etc.) belongs in a `core/` module, not the entry point.

**B3. Never access model attributes that aren't in the model definition**
Before referencing `obj.some_field` on an ORM model, confirm the field exists as a mapped column or relationship. Do not invent convenience fields that would be useful but aren't defined — they raise `AttributeError` at runtime.

**B4. No bare `pass` in stubs**
Always use `raise NotImplementedError("not yet implemented")`. A stub that raises fails loudly the moment it is hit; a `pass` silently does nothing and can go undetected for a long time.

**B5. No `__import__()`**
Top-of-file imports only. A dynamic `__import__()` inside an expression is a sign of confused code generation; restructure instead.

**B6. No dead branches**
No `if False:`, `if True:`, commented-out alternatives, or unreachable arms. Pick one approach and commit to it.

**B7. Account for all downstream resource creation**
Registration and creation flows must account for all downstream resource creation. If the architecture requires related rows in other tables when a new entity is created, create them in the same transaction or raise `NotImplementedError` with a clear comment if intentionally deferred. Never silently omit them.

**B8. Use async throughout**
`async def` route handlers, async ORM sessions, async cache clients. Do not mix sync blocking calls into async route handlers.

**B9. Business logic in services, not routers**
Routers validate input and return responses. All business logic lives in service classes. Routers call service methods — never raw queries directly.

## Testing

**T1. Test fixtures must match the actual endpoint response schema**
Before writing a fixture that reads a field from a response, verify that field exists in the declared `response_model`. Do not assume nested data is present without checking the schema. Example failure: reading `resp.json()["user"]["profile"]["id"]` when the endpoint only returns `{"access_token": "..."}`.

**T2. Use real dependencies in integration tests**
Do not mock the database in integration tests. A test suite that passes against mocks but fails against the real schema provides false confidence. Use an in-memory or test-schema instance of the real database engine.

## Infrastructure / DevOps

**I1. Follow the file layout in the plan exactly**
Do not create additional directories, duplicate config files, or parallel implementations beyond what the plan specifies. If the plan says `docker-compose.prod.yml` at the repo root, create exactly that file — not also a `deploy/docker-compose.prod.yml`. Extra files that reference each other inconsistently introduce bugs and ambiguity about which config is authoritative.

**I2. Include all required system dependencies in Dockerfiles**
Before writing a Dockerfile, identify every system-level dependency required by the Python packages in use (e.g. `libpq-dev` for asyncpg, `gdal-bin` for GeoAlchemy2). A missing system dep causes an `ImportError` at container startup — not at build time — making it hard to diagnose.

**I3. Use the correct CI platform**
Check which CI/CD platform the project uses before generating pipeline config. GitLab projects use `.gitlab-ci.yml`; GitHub projects use `.github/workflows/*.yml`. The syntax, service networking (alias vs localhost), and trigger syntax differ significantly between the two.
